### 2026-08-24 ｜ 前端大屏并发请求导致后端卡死（数据加载无互斥锁）

- **问题现象**
  后端自启动后，`POST /api/v1/aggregations/run` 单个请求超过 90s 无响应（curl 超时）；
  后端日志显示同一毫秒内涌入 **6 个并发聚合请求**，每个都打印
  `开始从 MySQL 加载数据`（同时触发 Spark JDBC 全量加载 209 万行），Spark local
  模式下互相抢占资源与 MySQL 连接，全部挂起，接口 120s 超时阈值内无法完成。

- **根因分析**
  `data_process/app/data/data_provider.py` 三个 Provider（CSV / MySQL / HDFS）的
  `dataframe()` 均为无锁惰性加载：
  ```python
  def dataframe(self) -> DataFrame:
      if self._df is None:
          self._load()      # 无锁！并发请求会同时进入并各自执行全量加载
      return self._df
  ```
  前端大屏（BigScreenView.vue）打开时会并行请求多个图表数据，首次访问
  `_df is None`，多个请求同时触发 200 万行全表加载 → 互相竞争卡死。
  单请求测试（26.6s 成功）无法暴露该问题，只有并发访问才触发。

- **修改文件**
  `data_process/app/data/data_provider.py`

- **修改方法**
  为三个 Provider 增加实例级 `threading.Lock()`，`dataframe()` 改为
  **双重检查锁（double-checked locking）**：
  ```python
  self._lock = threading.Lock()

  def dataframe(self) -> DataFrame:
      if self._df is None:
          with self._lock:
              if self._df is None:   # 只允许一个请求执行 _load，其余等待复用
                  self._load()
      return self._df
  ```
  首个请求独占加载，其余请求阻塞等待后直接复用同一个 DataFrame；
  同时顺带保护了 `_get_or_create_spark` 的并发创建。

- **验证结果**
  ⏳ 待验证：重启后端后并发请求应只触发一次加载，其余请求命中缓存。

### 2026-08-24 ｜ 后端启动失败：5000 端口被残留进程占用 + MySQL/Redis 未启动

- **问题现象**
  运行 `python run.py` 启动后端时，Flask 绑定 5000 端口失败，进程启动即退出；
  同时 MySQL（3306）与 Redis（6379）均未监听，数据源请求必然失败。

- **根因分析**
  1. **环境目录改名**：`D:\项目环境依赖` 已被改名为 `D:\Project_env`（摆脱中文路径），
     但 `D:\Project_env\start-db.bat` 仍引用旧路径 `subst Z: "D:\项目环境依赖"`，
     subst 映射失败 → 双击脚本时 MySQL/Redis 实际未启动；
  2. **端口被占**：上一次启动的 `python run.py` 进程（PID 57660）未正常退出，
     仍监听 5000 端口，新实例绑定冲突直接退出；
  3. 附：`start-db.bat` 内含中文注释，文件为 UTF-8 编码，cmd（GBK 代码页）解析错乱，
     报 `'click' 不是内部或外部命令` 等误报（不影响功能，但输出混乱）。

- **修改文件**
  - `D:\Project_env\start-db.bat`（环境脚本，非项目代码）

- **修改方法**
  1. 【环境】`Stop-Process` 清理残留后端进程（PID 57660），释放 5000 端口；
  2. 【环境】以新路径直接启动 MySQL 与 Redis：
     - `D:\Project_env\mysql-8.0.46-winx64\bin\mysqld.exe`（`--basedir`/`--datadir` 均指向新路径）
     - `D:\Project_env\Redis-8.6.3-Windows-x64-cygwin-with-Service\redis-server.exe`
  3. 【脚本】重写 `start-db.bat`：全部路径改为 `D:\Project_env`，删除 `subst` 依赖
     （目录已为纯英文，无需虚拟盘符）；注释全部改为 ASCII 避免 cmd/GBK 编码错乱。

- **验证结果**
  ✅ 已验证：MySQL `SELECT VERSION()` 返回 8.0.46，Redis `PONG`；
  后端启动日志 `缓存后端: Redis(127.0.0.1:6379/0)`，`health.status=ok` 且 `data_source=mysql://127.0.0.1:3306/medical_analytics/sparcs_discharge_2021`；
  `POST /api/v1/aggregations/run` 首次聚合 **26.6s** 成功返回 5 家医院真实数据（2,094,484 行），
  第二次 `cached=true`，`query_time` 0.03s。

### 2026-08-23 ｜ MySQL 数据源加载超时/失败（Spark JDBC 单分区全表扫描）

- **问题现象**
  后端切换 `data_source=mysql` 后，`POST /api/v1/aggregations/run` 返回 500：
  `Spark 聚合计算失败，请检查参数后重试`，后端日志显示耗时 **234s** 且触发慢查询告警（阈值 5s），接口超时阈值 120s 被突破。

- **根因分析**
  1. 缺少 MySQL Connector/J 驱动 jar：`ClassNotFoundException: com.mysql.cj.jdbc.Driver`（Spark 是 JVM，读 MySQL 必须 JDBC 驱动，PyMySQL 只用于 Python 层入库）；
  2. 驱动就位后，`MySQLDataProvider._load` 使用 **Spark JDBC 单分区全表读取** 200 万行大文本数据，耗时约 234s，超过接口超时导致失败；
  3. 本机存在**两个 mysqld 进程**共用同一 datadir（PID 16168 挂起 + PID 37952 服务），导致 Spark 侧连接间歇性被拒（`ConnectionRefusedError 10061`）。

- **修改/处理**
  1. 【环境】复制 `D:\实习\大数据配套工具包\mysql-connector-java-8.0.30.jar` → `D:\Miniconda\envs\analytics\Lib\site-packages\pyspark\jars\`；
  2. 【环境】停止挂起的 mysqld 进程（PID 16168），保留服务实例（PID 37952）；
  3. 【代码】`data_process/app/data/data_provider.py` 的 `MySQLDataProvider._load`：先查询 `MAX(id)` 上界，按自增主键 `id` 分成 **8 个分区** 并行读取（`partitionColumn/numPartitions/lowerBound/upperBound`），显著缩短加载时间；无 `id` 主键的老表自动回退单分区。

- **验证结果**
  ✅ 已验证：分区读取生效，首次聚合查询 **17s** 成功返回（2,094,484 行数据完好），第二次查询 `cached=True` 命中 Redis 缓存

### 2026-08-23 ｜ Spark 加载 MySQL 全表内存溢出（Java heap space）

- **问题现象**
  分区读取后聚合查询仍 500，后端日志根因：`java.lang.OutOfMemoryError: Java heap space`（JDBC 读取任务阶段 OOM）。

- **根因分析**
  Spark 默认 `spark.driver.memory=2g`，`MySQLDataProvider._load` 中 `df.cache()` 需要把 210 万行 × 33 字段（含大文本列）驻留 JVM 堆，2g 不够。

- **修改方法**
  `.env` 增加 `ANALYTICS_SPARK_DRIVER_MEMORY=4g`（本机 16G 内存，环境变量覆盖默认值，未改代码）。

- **验证结果**
  ✅ 已验证：聚合查询 17s 成功返回，无 OOM。

### 2026-08-23 ｜ Redis 缓存连接失败，自动降级为进程内缓存

- **问题现象**
  后端启动时日志输出：
  ```
  Redis ping 失败: AbstractConnection.__init__() got an unexpected keyword argument 'connect_timeout'
  Redis 连接失败，降级为进程内缓存
  ```
  `GET /api/v1/health` 中 `cache.backend` 显示 `in-memory-ttl-lru`，而非 `redis`。

- **根因分析**
  `data_process/app/core/cache.py` 的 `RedisCacheBackend.__init__` 将参数名 `connect_timeout` 原样传给
  `redis.ConnectionPool(**kwargs)`。redis-py 的连接参数标准名称为 `socket_connect_timeout`，
  `connect_timeout` 不是合法参数，导致 `ConnectionPool` 初始化抛出
  `TypeError`，缓存后端按"连接失败"降级为进程内缓存。
  该问题与 redis-py 版本无关（5.x ~ 8.x 均不接受 `connect_timeout`）。

- **修改文件**
  `data_process/app/core/cache.py`（第 159 行）

- **修改方法**
  ```
  - "connect_timeout": float(connect_timeout),
  + "socket_connect_timeout": float(connect_timeout),
  ```
  即把 Redis 连接超时参数名改为 redis-py 标准名称 `socket_connect_timeout`。

- **验证结果**
  ✅ 已验证：重启后端后日志显示 `缓存后端: Redis(127.0.0.1:6379/0)`，`health.cache.backend = redis` 且 `connected=true`

## 三、修改流程约定

1. 修改前先复现/确认问题，记录问题现象；
2. 修改时保持最小改动，不影响其他功能；
3. 修改后在本文件追加记录并填写验证结果；
4. 涉及他人负责模块（如后端组员代码）的修改，本地验证后需与对应人员同步，避免直接覆盖他人工作。
